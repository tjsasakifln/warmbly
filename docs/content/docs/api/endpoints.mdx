title: Endpoint scope map
description: Every endpoint, which auth types it accepts, and which permission it requires.
---

This page is the source of truth for what an API key can and cannot reach. Every route in the backend falls into one of three buckets:

- **API key accepted**: works with both a JWT (dashboard user) and an API key with the listed permission.
- **JWT only**: never reachable via an API key. Used for billing, governance, websocket bootstrap, danger-zone destruction, the OAuth onboarding flow, and admin tools.
- **Public**: no auth required (webhooks with signature verification, health check, OAuth bouncer pages).

When an endpoint says "JWT permission: X / API permission: Y", the dual-auth middleware checks the relevant one based on which credential the caller used.

All paths below are relative to the versioned base URL `https://api.warmbly.com/v1` (for example `/campaigns` is `https://api.warmbly.com/v1/campaigns`). See [versioning](/api/) for details.

`POST /campaigns/:id/start` runs recipient verification before scheduling. It verifies up to 100 unchecked recipients per request and stores `verification_status`, `verification_summary`, and `verification_checked_at`, which are returned on campaign reads. A `409 campaign_verification_pending` means verification is still progressing and the start can be retried. A projected hard-bounce rate above `5%` returns `422 campaign_projected_bounce_rate_high`; a rate from `2%` through `5%`, or any risky recipient, records a warning but allows the campaign to start.

`GET /contacts/custom-fields` lists the distinct custom-field keys used across your contacts (frequency-ranked), for building personalization pickers. It returns a flat string array under `data`, capped at 200 keys.

`GET /confenge/status` reports authoritative feed age separately from sync time, and reports commercial qualification separately from both. `feed_authority_state` and `feed_source_expires_at` describe acquisition health only: they never block outbound for a commercially qualified population. `feed_last_attempt_at`, `feed_last_attempt_status`, and `feed_last_attempt_error` expose the newest sync attempt without erasing the last completely applied snapshot reported by `feed_last_success_at`. A completed sync reports `counts.feed_lineage_committed=1`; accounts and touchpoints from runs without that marker remain fail-closed. The readiness payload exposes `target_membership_complete`, `target_membership_count`, and `supplier_confirmed_count`, plus `commercial_qualification_state` (`QUALIFIED`, `EXPIRED`, `REVOKED`, `UNKNOWN`), `commercial_qualification_known`, and the `commercial_qualified_count`, `commercial_expired_count`, `commercial_revoked_count`, and `commercial_unknown_count` rollups. Incomplete authority and an unverified population both remain fail-closed.

`GET /confenge/dispatch/status` reports configured mailbox envelopes and observed transport facts separately. Every organization mailbox appears, including a mailbox with missing credentials, so absence cannot disappear from the capacity readback. Each mailbox includes enabled state, provider type, worker assignment, worker heartbeat health, SPF/DKIM/DMARC state, mailbox and warmup age when known, configured daily cap, minimum wait, derived hourly cap, business window, latest attempt/acceptance/bounce/complaint/reply/provider rejection, health reason, pause source, and next eligible slot. Provider ceilings and unobserved operational facts remain listed under `unknown` until an explicit source is stored. The aggregate forecast reports effective and potential slots for 24 hours and 7 days, plus estimated queue drain time when transport has effective capacity. While paused, effective next-slot fields are absent because resume time is unknown. A slot is capacity for an attempt, not a delivery promise. Pause readback is additive: `paused_by` (API actor, when one exists), `paused_at`, `pause_source`, and `pause_sources`. `pause_source` is the most restrictive active path (`api`, `kill_switch_file`, `worker_guard`, `environment`, or `durable_control`). A file-only or worker-only pause does not inherit a Control Center actor. An unreadable pause source fails closed. `POST /confenge/dispatch/resume` cannot clear a remaining restrictive source. `POST /confenge/dispatch/pause` and `POST /confenge/dispatch/resume` are naturally idempotent state assignments and keep the file and durable kill controls authoritative.

`POST /confenge/sync` validates and imports a complete `confenge.outreach.manifest.v1`, resumes stale chunk leases idempotently, and publishes a new current run only after the account denominator and prepared `INITIAL` backlog close. The response includes `imported`, `supplier_confirmed`, `candidate_attributed`, `initial_touchpoint_prepared`, `delegated_eligible`, `held_exception`, and `stale_initial_retired` under `data.counts`. A replay of the same snapshot is a `noop` with the stored counts.

`GET /confenge/inbound` is the INBOUND NOW queue. Default `include_synthetic=0`. `POST /confenge/inbound/:leadId/acknowledge` records a human acknowledgement (actor required, idempotent). `POST /confenge/inbound/:leadId/resolve` records a no-action resolution with a reason code. Neither contacts the lead nor sets WON, LOST, pipeline, or revenue. `POST /confenge/inbound/:leadId/outcome` remains the first-action registrar.

`GET /confenge/intel/outcome-feedback` returns the read-only `confenge.acquisition_outcome_feedback.v1` aggregate for inclusive `from` / `to` UTC cohort months (`YYYY-MM`, current plus previous two months by default). It separates receipts, leads, observed QCOs, chain and strictly joined native proposals, privacy-safe native proposal states and proposed value by currency, human-confirmed outcomes, contracted/received value by currency, contracts, and margin. A validated lead is not QCO. Native proposals require one exact safe correlation/account/opportunity association, matching the lead ID when `source_lead_id` is present, matching record kind, and an observed sent state; drafts and ambiguous/conflicting/held/invalid rows remain unknown. Proposal amount is minor-unit quote value, never contract, contracted revenue, received revenue, or margin. Contracted/received amounts are never summed across currencies, and arithmetic overflow fails closed. Missing contract or margin evidence stays `UNJOINABLE` / `UNKNOWN`, never zero. Direct closed-context/month/record-kind cells below five stable account privacy units are combined into a dimensionless roll-up; if that roll-up is also below five, its counts and values are null. Receipt, lead, QCO, proposal, each proposal state/currency, WON, LOST, and each contracted/received currency stage require five account contributors independently. Synthetic and real thresholds never mix. Raw landing path, asset ID, CTA ID, intent class, and buyer job stay `UNJOINABLE` / `UNKNOWN` until closed versioned registries exist. The response contains no lead/receipt/correlation/account/person/proposal/payment identity or free text, performs only SELECT reads of existing chains and latest observed-sent native proposal versions, and never writes upstream.

`GET /confenge/intel/executive` is the monthly commercial-intelligence query (not a CRM board). Families stay separate. Real counts stay empty or `UNKNOWN` until a human-approved action exists. `include_synthetic=1` is the labeled fixture path. WON is never inferred. `causal_proof` is always false. `weekly_revenue_chains` exposes opaque `account_id`, `opportunity_id`, `offer_id`, `proposal_id`, `charge_id`, and `payment_id` under one `correlation_id`. It also exposes the latest deliverable, evidence, `GO`, `NO-GO`, or `WAIT` decision, responsible role, deadline, next action, proposal, charge, and receipt. Missing facts use `availability: "UNKNOWN"`; they are never represented as zero. Canonical identifiers are limited to 160 characters and reject whitespace, email addresses, and obvious PII tokens. Accounts and offers may participate in multiple correlations. Opportunity, proposal, charge, and payment IDs cannot be rebound to another correlation. A pre-existing correlation under a legacy fragmented identity stays held for operator reconciliation instead of being merged automatically. A provider `payment_received` without a positive observed amount stays held and does not fall back to a catalog price.

`GET /confenge/intel/scoreboard` is the seven-stage inbound truth placar (URLs live/indexable, non-branded impressions/clicks, CTA completed, lead persisted, qualified conversation, proposal emitted, revenue received). Default `include_synthetic=0`. Pipeline contracted, MRR, charge created, and cash received stay on `separate_metrics`. Missing GSC or URL-index ingest stays `BLOCKED`. `POST /confenge/intel/human-outcomes` records a founder action/outcome. WON, LOST, and received revenue require human/document evidence. `GET /confenge/intel/human-envelopes` returns empty EXTRA / ACCOUNT_1 / ACCOUNT_2 / ACCOUNT_3 slots with blank IDs.

`GET /confenge/intel/organic-scoreboard` is the organic cohort/asset/landing placar (`confenge.organic_learning_scoreboard.v1`). Layers stay separate: discovery (ELIGIBLE/APPEARED/CLICKED/ENGAGED only when web-cfg aggregates arrive, otherwise BLOCKED), lead, qualification, first action, conversation, meeting, proposal, pipeline, WON/LOST/UNKNOWN, contracted vs received revenue. Windows are complete 7d, complete 28d, 90d, and open/censored cohorts. `organic_search`, `ai_referral`, `direct`, `partner`, `outbound`, `referral`, and `unknown` never mix. Individual GSC queries are not stored. Organic ROAS/CAC stay BLOCKED without complete cost and observed received revenue.

`GET /confenge/intel/organic-feedback` is the versioned editorial export (`confenge.organic_editorial_feedback.v1`) with `REPEAT` / `CHANGE` / `STOP` / `NEED_MORE_DATA`, denominators, freshness, reason codes, and explicit uncertainty. `causal_proof` is always false. `upstream_writes` is always empty. Warmbly does not write web-cfg.

`POST /confenge/intel/events` ingests one versioned commercial event (`confenge.commercial_event.v1`). Same `event_id` or idempotency key is a replay. Lead, page view, citation, and X-Ray completion never become pipeline. Pipeline never becomes revenue. Checkout, payment, subscription, and provider object creation are not received revenue. Onboarding starts only after a reconciled financial confirmation. `type=search_observation` with `version=confenge.search_observation.v1` persists an aggregated discovery snapshot (nullable counts, no individual query) and echoes `persisted`, `replay`, `not_a_lead=true`. Unknown versions return 4xx and do not persist a chain.

Public `GET /api/v1/webhooks/confenge/inbound/health` advertises `accepted_event_versions` including `confenge.commercial_event.v1` and `confenge.search_observation.v1`. The HMAC inbound webhook accepts that observation envelope on the same route as lead handoff without creating a lead. A `confenge.commercial_event.v1` body on the same HMAC route is a commercial receipt, not a lead: same `provider_event_id` (or `event_id`) is a replay, invalid secret is 401, unknown types are preserved as UNKNOWN, and checkout/subscription/callback creation is not received revenue. `GET /confenge/intel/executive` exposes `by_offer_version` counters plus stage timestamps. Onboarding is `ONBOARDING_BLOCKED`, `ONBOARDING_ELIGIBLE`, `ONBOARDING_STARTED`, or `SERVICE_ACTIVE`.

`POST /confenge/intel/commercial` is the authenticated manual-first operator path (register offer/terms/capacity, attach already-created provider IDs, record a financial event with evidence and review status, start onboarding after the gate, or apply a HumanCorrection). It does not call Asaas. `GET /confenge/intel/commercial/:leadId` returns the canonical timeline. `POST /confenge/intel/commercial/provider-events` persist-first acks a signed sandbox provider event. An invalid signature returns `401`; a signed malformed payload returns `422`. A receipt or chain-store outage returns `503 service_unavailable`; retry with the same provider event ID. `POST /confenge/intel/exceptions/:id/reopen` reopens a resolved exception. None of these routes are public.

The deployment edge exposes only `POST /api/v1/webhooks/asaas` and `GET /api/v1/webhooks/asaas/health` for Asaas transport. The POST validates the configured `asaas-access-token`, minimizes the payload, deduplicates by provider event `id`, commits it to the local SQLite queue, and only then returns HTTP 200. Background delivery interprets the Warmbly response body: `held`, `rejected`, or `processed=false` becomes a durable blocked occurrence, not success. Retry exhaustion becomes dead-letter state with owner and next action. The health response contains state counts, oldest backlog age, open occurrence count, and backup freshness, never event payloads. This edge never creates or mutates an Asaas customer, checkout, subscription, or payment.

`GET /confenge/intel/report` is the inbound learning observability payload (IQP, lanes, exceptions, latency baseline, learning candidates, `READY_FOR_REAL_EVENTS` / `ADJUST` / `NO_GO`). It is not a CRM and not a forecast.

`GET /confenge/intel/exceptions` is the operator queue. Filter with `type`, `lane`, `source`, `severity`, `status`, `age_min_seconds`, and `age_max_seconds`. Each row includes evidence, history, `next_action` or an explicit open status, and only the legal actions `link`, `defer`, `reject`, and `mark_external_evidence_required`. `GET /confenge/intel/exceptions/:id` is the detail. `POST /confenge/intel/exceptions/:id/resolve` records before/after, actor, and reason. Send `Idempotency-Key`. The same command replays the first result. Illegal lifecycle moves and any attempt to invent WON, LOST, revenue, or identity are refused and the exception stays open.

`GET /confenge/cohorts/:id` returns one immutable cohort version with its manifest, candidates, review and scheduling state, plus the editorial verdict on the frozen copy: `editorial_state` (`CURRENT` or `LEGACY_SUPERSEDED`), `actionable`, `editorial_reason_codes`, `editorial_notice`, and the pointers `is_current_version`, `current_version` and `current_version_id`. Historical GO/NO-GO data may still appear as read-only audit. Each candidate repeats `editorial_state`, `actionable` and `editorial_reason_codes`, and a superseded candidate carries the same codes in `blocked_by`. A version is current only when the version stamp and every member stamp are current.

`POST /confenge/cohorts` accepts at most ten members. `selection_mode=NEXT_UNCLAIMED` reserves the next disjoint suppliers in a server-managed transaction; `selection_mode=RECOVER_PRIOR` accepts `recover_version_ids` and re-evaluates those suppliers against the current canonical source. The API exposes no offset. It reports aggregate selection progress and never inherits validation, review, approval or scheduling into a recovered cohort.

Superseded copy is readable and never operational. `POST /confenge/cohorts/:id/candidates/:candidateId/review` refuses `decision=APPROVE` with `409` and code `composer_superseded` (`HOLD` and `REJECT` still work). `POST /confenge/cohorts/:id/recompose` is the way forward: it forks version N+1 with the current composer, requires `Idempotency-Key`, `reason`, `confirmation` and `expected_frozen_hash`, preserves every recipient and provenance fact byte-identical (drift is refused, not stored), and is born with no validation, no review, no approval and no scheduling.

`GET /confenge/review/drafts` (and its alias `GET /confenge/touchpoints/review`) returns the same verdict per row as `editorial_state`, `editorial_actionable`, `editorial_reason_codes`, `editorial_notice`, `composer_version` and `prompt_version`, alongside the judging context `route_class`, `fact_source` and `target_fit`. Next to superseded copy `composer_version` is empty on purpose, because naming the current composer there would read as if it wrote the text. `POST /confenge/touchpoints/:id/approve`, `POST /confenge/touchpoints/:id/queue`, and `POST /confenge/review/drafts/:id/decision` when the decision approves return `409` on a draft an earlier composer wrote, and transport refuses the send grant by the same rule. See [CONFENGE editorial lifecycle](/guides/confenge-editorial-lifecycle/) and [error codes](/api/error-codes/).

`GET /confenge/first-touch/status` returns `schema_version=warmbly.confenge.first-touch-control.v1`, delegated decision readback, and one aggregated `control` snapshot. The snapshot binds the current source run, snapshot, freshness expiry and complete membership to prepared, READY, delegated, human, queued and reserved counts. It also exposes the next and furthest `due_at`, provider attempts, provider acceptances, sent count, outcome counts, kill switch, dispatch pause, mailbox capacity, and one fail-closed blocker. Its `runway` section includes the capacity-derived target count and horizon, mailbox and daily capacity, recent fill rate, stale retirements, holds and no-candidate counts. A paused transport can retain a large prepared reservoir and bounded future runway. Queue depth is inventory, not send velocity.

`POST /contacts/import/commit` statically classifies every mapped address before writing contacts. Successful responses include `quality` with invalid, disposable, role-based, risky-TLD, and combined bad-address counts. An import whose invalid plus disposable share is above `25%` is recorded for review and rejected with `422 contact_import_quality_blocked` before any contacts are written. The error response includes the same aggregate import result under `details` so clients can explain the block without parsing the message.

AI contact research charges credits (2 per run, billable even when it finds nothing) and only saves cited findings. See the [AI contact research](/guides/ai-contact-research/) guide. The batch endpoint accepts up to 500 contact ids and drains in the background.

`POST /unibox/reply/draft` returns an AI-drafted reply (it never sends) grounded in the thread, the contact, and your [voice profile](/guides/unibox/#ai-reply-drafts). It charges AI credits; see [AI credits](/guides/ai-credits/).

`POST /unibox/compose/draft` returns a grounded AI draft for a new email (it never sends): the recipient's contact record, correspondence history, and the workspace voice profile feed the prompt, and the response carries either `text` or a clarifying `question` plus a `grounding` report. Charges AI credits like the reply draft; see [AI credits](/guides/ai-credits/).

`POST /unibox/compose` sends a brand-new outbound email (not a reply). Omit `email_account_id` (or pass `"auto"`) and the backend picks the best mailbox for the first recipient; the response reports `account_id`, `account_email`, `auto`, and a `picked_reason`. Recipients on the workspace suppression list are rejected with a `400` before anything queues. `GET /unibox/compose/candidates?to=<address>` returns every active mailbox scored for that recipient (conversation history, remaining daily budget, domain-auth health) plus the resolved contact and suppression state; see [composing email](/guides/unibox/#composing-a-new-email).

The `/unibox/drafts` endpoints hold autosaved compose drafts, scoped to the calling user within the organization. The draft id is client-generated, so `PUT` is idempotent (safe for debounced autosave and retries); deleting a missing draft is a no-op.

`GET /unibox` also accepts `address=<value>` (matches sender or recipient, for "every conversation with this person") and `direction=sent|received` (resolved against your own mailbox addresses).

The `agent-drafts` endpoints back the [inbox agent](/guides/inbox-agent/): the agent drafts a suggested reply on an inbound human reply and holds it here for review. `GET` lists the pending drafts; `approve` sends one (optionally with an edited `body`) through the normal reply path and is safe to retry with an `Idempotency-Key`; `discard` dismisses it. Approving is the only path that sends.

### Retry safety

Mutating API requests may include an `Idempotency-Key` header. Warmbly stores the completed response for 24 hours per organization and key. Reusing the same key with the same method, route, query, and body replays the original response with `X-Idempotent-Replayed: true`; reusing the key with a different request returns `409 Conflict`.

## MCP server

`POST /v1/mcp` exposes the tool registry over the [Model Context Protocol](/api/mcp/) streamable-HTTP transport. It accepts an API key or an OAuth 2.1 access token (an unauthenticated request gets the RFC 9728 discovery challenge). Each tool is gated by its scope, `tools/list` reflects only what the credential allows, and send-class tools are never exposed. Per-key rate limits apply.

## Notes

- When a route has both a JWT permission and an API permission listed, the dual-auth middleware checks the JWT user's organization role for browser callers and the key's permission bitmask for API key callers. They're independent gates: a user's role doesn't constrain what an API key can do beyond what was granted at creation.
- Every API key request is logged to `api_key_usage_logs` with the endpoint pattern (e.g. `/campaigns/:id`), method, IP, user-agent, response status, and elapsed milliseconds. JWT requests are not logged here.
- Rate limit categories (`X-RateLimit-*` headers) are scoped to the underlying user, not the key; every key issued by a user shares the user's quota.
