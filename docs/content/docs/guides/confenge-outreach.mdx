---
title: CONFENGE outreach staging
description: Import versioned commercial feeds and authorize outbound with exact human review or the delegated first-touch policy.
---

CONFENGE outreach is an optional, feature-flagged staging layer. It lets an organization import a versioned commercial feed (for example from `extra-cli`) into Warmbly so companies can sit in a queue even when no verified email exists yet.

Warmbly stays the execution plane: contacts, mailboxes, campaigns, inbox, CRM. The intelligence plane (datalake, signals, evidence scoring) stays outside Warmbly. Warmbly never connects to that database and never writes into it.

## Enable

Set on the backend:

```env
CONFENGE_OUTREACH_ENABLED=true
```

`CONFENGE_AUTO_SEND_ENABLED`, `CONFENGE_GREEN_AUTORUN_ENABLED`, and `CONFENGE_REQUIRE_HUMAN_APPROVAL=false` cannot be activated. Startup, enroll, queue, and the worker transport boundary fail closed. Bulk green-autorun endpoints create zero send jobs. Human approval remains the default authorization path.

The CONFENGE first-touch campaign has one narrow exception. `CONFENGE_DELEGATED_FIRST_TOUCH_ENABLED=true` permits only `CFG-FIRST-TOUCH-ROUTING-v1` after proving the company is the private supplier, reconciling a published mailbox, running adversarial QA, and binding the exact evidence and content hashes. The decision is recorded as `DELEGATED_POLICY_APPROVE`, `approved_by` remains empty, and the canonical scheduler performs a database readback before the item counts as queued. Suppression, opt-out, bounce, reply, kill switch, mailbox limits, business windows, and the live policy grant remain final gates. The flag defaults to `false`.

`CONFENGE_DELEGATED_FIRST_TOUCH_AUTORUN_ENABLED=true` starts the rolling evaluator for that same narrow policy. It keeps at most one first touch in the canonical dispatch queue, converts ordinary QA failures into exceptions, and replenishes the next eligible item after dispatch. It does not enable legacy auto-send or GREEN autorun, create another queue, or bypass any send-time gate. The flag defaults to `false`.

The canonical campaign remains active while the current completed feed has prepared first touches that the delegated worker has not decided. This covers the short interval after a feed refresh cancels a stale queue and before the worker writes the replacement queue. Only a current `NEEDS_REVIEW` first touch under the active founder policy keeps the campaign alive. An exhausted ordinary campaign still completes, and pending work still needs the full delegated checks before it can become `QUEUED` or transportable.

An upstream controlled route never overrides mailbox-purpose suppression. Addresses classified as blocked for sending or as an unsuitable mailbox stay out of delegated approval even when their route class is otherwise allowed.

For a manual batch, the agent first writes a research manifest containing candidate IDs, public evidence and copy, but no mailbox address. `confenge first-touch seal` reads the selected mailbox from the operational database, derives its route class, binds the subject and body hashes, and creates a new mode `0600` manifest without printing the address. `confenge first-touch apply --dry-run` validates that sealed artifact before the confirmed write path records approval and canonical queue readback. Autorun constructs the same manifest from current persisted supplier, recipient, feed, and evidence records, then sends it through the same validator and apply path.

Delegated copy uses `confenge.composer.v7` and the versioned
`confenge.first-touch-copy-rules.v1` contract. It does not rotate synonyms or
choose prose from a UUID. The deterministic brief may use only the company,
confirmed supplier role, a public fact bound to current `CONFIRMED_FACT`
evidence, service code, route class and recipient purpose. If a specific fact
cannot be supported, the composer uses a short supplier-role message instead of
inventing detail. `DIRECT_PERSON` uses a first name only when the selected route
has person evidence. Role, generic and company-attributed freemail routes ask
for the appropriate internal routing without pretending to reach a decision
maker. Every message includes a plain request to say if further contact is not
wanted.

Corpus QA measures exact and semantic near duplicates, subject, opening,
practice-line and CTA concentration, evidence support, metadata leakage,
route-class fit and length. Exact content reuse, unsupported claims,
buyer/supplier inversion, guessed people, empty copy, internal metadata,
offensive or manipulative language and route-inappropriate CTAs fail closed.
Concentration is attributed to its factual dimension instead of compared with
a hidden percentage. A repeated practice line is valid when it follows the
actual `service_code` distribution; the composer never creates cosmetic
variants to disguise it.

Optional feed source:

```env
CONFENGE_EXTRA_CLI_FEED_URL=https://feed.example.com/confenge/outreach.json
CONFENGE_EXTRA_CLI_FEED_TOKEN=
CONFENGE_EXTRA_CLI_ALLOWED_HOSTS=feed.example.com
CONFENGE_FEED_MAX_AGE=24h
```

In production the feed URL must be HTTPS and the host must be on the allowlist. Local development may use a `file://` path.

## Dedicated operator dashboard

The isolated CONFENGE deployment can expose a focused PT-BR dashboard without an interactive sign-in:

```env
CONFENGE_OPERATOR_MODE=true
CONFENGE_OPERATOR_USER_ID=11111111-0000-0000-0000-000000000001
CONFENGE_OPERATOR_ORG_ID=22222222-0000-0000-0000-000000000001
```

This mode is disabled by default in Warmbly. It must only be enabled when both the dashboard and API bind to loopback and operators connect through an SSH tunnel. The configured user must be active, accepted into the organization, and have view and manage contacts permissions. Invalid configuration fails startup.

The browser skips login, registration, workspace selection, and onboarding. Internally it receives a normal organization-scoped JWT session, so the existing permission gates, human approval controls, idempotency, and audit attribution remain active. All browser actions are attributed to the configured technical operator.

## Recipient and messageability gates

Every target ends in `VALIDATED`, `CONTROLLED_ELIGIBLE`, `EXCEPTION`, or `BLOCKED`. A public role, department, generic-company, or company-associated freemail route may be `CONTROLLED_ELIGIBLE` without a known person, but it is never auto-promoted to `VALIDATED`. Warmbly never invents a name, role, ownership, personal email, consent, or evidence. Pre-contract institutional candidates remain eligible only when the imported record already says `email_send_ready=true`, `COMPANY_OWNED`, carries a defensible public verification status, and is not inferred, suppressed, blocked, bounced, or freemail without explicit company evidence.

Copy is planned only after extra-cli intelligence is reduced to an internal `OutreachStrategy`. The messageability gate then decides `READY`, `NEEDS_ENRICHMENT`, or `BLOCKED`. Only a `READY` plan is rendered into recipient-safe facing copy (greeting, public observation, relevance, micro-offer, CTA). Internal hypothesis, rationale, and operator warnings never enter the email. `validation_ok=true` means the exact body has passed deterministic QA, not that it is authorized. It proceeds either through human review or, for an eligible first touch only, through `CFG-FIRST-TOUCH-ROUTING-v1`. Unready items go to a separate exception or enrichment queue. Passive MX or DNS from extra-cli never becomes `VERIFIED`, `VALIDATED`, or `email_send_ready`.

`NEEDS_REVIEW` is assigned only when recipient resolution is `VALIDATED` or `CONTROLLED_ELIGIBLE`, messageability is `READY`, and the composed body is non-empty. `CONTROLLED_ELIGIBLE` preserves the institutional route class and an unknown person instead of pretending to validate an individual. An `EXCEPTION` never becomes `NEEDS_REVIEW`. Two individually valid named humans on the same account stay `EXCEPTION` and land in `MANUAL_OUTREACH` until a human picks one recipient.

Human `APPROVE`, `EDIT`, `REJECT`, `RECIPIENT_CHANGE`, and `SKIP` persist as `HumanCorrection`. Edits keep before/after. The delegated exception does not apply to follow-ups, replies, WhatsApp, conflict resolution, or copy without complete evidence.

## Message authorization

Every CONFENGE outbound message needs exact, durable authorization before it can enter the send queue. Follow-ups, replies, WhatsApp, and ordinary campaign messages require explicit human approval. A standard first-touch routing email may instead use the active delegated policy described above.

Flow:

1. Plan a cadence for an account (initial touch plus spaced follow-ups).
2. When a touch is due, generate the message text just-in-time (prior touches, outcomes, latest imported context).
3. The human path reviews the exact recipient, channel, subject/body, fact and evidence. The delegated path proves contractor role and mailbox association, then runs independent adversarial QA.
4. Human edits clear prior human approval. Agent copy failures may be repaired and reviewed again, while factual failures stay on hold.
5. A valid authorization schedules the exact hash for the next eligible business window. It never sends immediately.

Authorization is **per touch**, never for a whole sequence or account. There is no “approve whole sequence” action.

Transport is blocked unless the durable touchpoint has a matching content hash and either a human `approved_by` or an exact delegated decision bound to a live policy grant. Draft-only approval is not enough to send.

Cadence uses a versioned policy (`confenge.cadence.v1`): initial touch plus spaced follow-ups with no false urgency. Channel is chosen at touch time. Follow-ups are not a fixed multi-step campaign sequence that auto-fires after the first enrollment.

Dominant stops: `DO_NOT_CONTACT`, opt-out, bounce, and human reply cancel open future touches atomically. Reimport does not reactivate `SENT` or `DNC` touchpoints.

Approval is also bounded in time, not only in scope. Frozen copy can be approved, authorized, queued and sent only while the composer that wrote it is the one the platform ships. Copy from an earlier composer becomes `LEGACY_SUPERSEDED`: readable for audit, refused by every operational path, and moved forward by recomposing the cohort into a new version. See [CONFENGE editorial lifecycle](/guides/confenge-editorial-lifecycle/).

## Delivery and reply reconciliation

The commercial chain is the authoritative record for outbound transport outcomes. An `attempted` fact is recorded at the worker transport boundary. A provider acceptance is recorded as `accepted`, not as delivery. `delivered` is recorded only when a provider or delivery-status notification reports it explicitly. If transport reaches an ambiguous final state, the chain preserves `delivery_unknown` as UNKNOWN until stronger evidence arrives.

Hard bounces and complaints suppress the exact recipient address in the canonical suppression store. They cancel queued work for that address without invalidating the whole company or another mailbox at the same company. Soft bounces remain soft and do not become permanent suppression without later evidence. A missing reply is not evidence of a bad mailbox.

Unsubscribe and opt-out events record their reason, source, and timestamp against the exact recipient scope. The final `AssertTransportable` database read checks that canonical suppression immediately before provider transport, including for an item that was approved and queued before the suppression arrived.

A human reply marks the correlated touchpoint, stops incompatible future attempts for the account, and enters the existing human triage flow. It never triggers an automatic reply in the CONFENGE flow. Positive, routed, and ordinary replies remain distinct commercial facts. Duplicate or replayed provider events reuse stable receipts, while out-of-order or impossible transitions retain the observed fact and enter the existing exception queue for reconciliation.

Operational outcome metrics contain only opaque dimensions: `route_class`, `source`, `source_run`, `cohort`, and sender `mailbox`. Recipient addresses and company names are not metric dimensions.

## Import

`POST /api/v1/confenge/import` accepts:

- the full feed JSON body (`schema_version: confenge.outreach.v1`; legacy shapes remain auditable but are not outreach-eligible)
- the extra-cli operator pack (`cards.json`) or `confenge.decision_unit_account.v1` accounts. Routed calls and manual lanes import as first-class work even when no email is VALIDATED
- or `{"uri":"https://...","dry_run":true}` to fetch then import

The import printout includes the operator summary: actionable accounts, route distribution, number requiring a manual call, number that are email-safe, unresolved blockers, and the next human actions. Re-import of the same extra-cli identity does not create a second account.

Use `?dry_run=true` for counts only (`creates`, `updates`, `unchanged`, `missing_contact`, and related fields). Send `Idempotency-Key` for safe retries.

Companies with eligible current target-fit but no enrollable contact enter as `NEEDS_CONTACT`. They are not discarded and are not forced into the contacts table.

## Target-fit authorization

`extra-cli` is the sole authority for CONFENGE target-fit. Warmbly does not infer ICP membership from company names, industry text, public contracts, email availability, old scores, or prior `enrollable` values.

Outbound requires all of the following at the same time:

- `target_fit_class` is `TARGET_CONFIRMED`
- `target_fit_fresh` is explicitly `true`
- `target_fit_version`, `target_fit_source_watermark`, and a comparable observed timestamp are present
- any supplied `target_fit_send_tier` is eligible under the imported contract
- the company and selected contact both have imported `email_send_ready=true`
- DNC, reply, bounce, suppression, provenance, approval, and dispatch gates still pass

Missing, stale, contradictory, out-of-scope, or downgraded target-fit fails closed. A valid company email does not compensate for missing commercial authorization.

An ineligible import keeps the account and its history, assigns a `TARGET_FIT_*` suppression reason, cancels open touchpoints and dispatch items, blocks unsent drafts, and detaches queued campaign enrollment. A later older watermark cannot restore eligibility. The same authorization is reloaded immediately before campaign transport, so an already approved or queued item cannot send after a downgrade.

The **Agora** lane applies the complete target-fit and contact gates in its server-side query. It means the company can legitimately receive an outbound action now, not merely that a contact exists.

## Reimport rules

Reimport updates machine-owned fields (priority, moment, offer, messaging, evidence). It preserves:

- human `DO_NOT_CONTACT` and block flags
- post-send queue states (enrolled, sent, replied, and later CRM states)
- terminal touchpoint states (`SENT`, `DNC`, and other closed states)

Target-fit is updated only by a current authoritative decision. A downgrade takes effect immediately across planning, generation, approval, enrollment, and the final send gate. Imports with an older decision watermark cannot overwrite a newer restriction.

## Dashboard

The CONFENGE page is a PT-BR commercial operations center. Its first-touch policy panel separates `DELEGATED_POLICY_APPROVE`, human approvals, canonical queue readbacks, and HOLD/CANCELLED exceptions. It exposes the active policy version plus per-item supplier, recipient class, evidence reference, reason codes, due time, runtime SHA, and readback. Eligible first touches do not inflate the human review queue. `NEEDS_REVIEW` represents an exception or an explicitly human-operated flow. The release evaluator accepts either an exact human approval set or an exact `DELEGATED_POLICY_APPROVE` set bound to `CFG-FIRST-TOUCH-ROUTING-v1`; an absent count, policy drift, or decision-source drift remains `NO_GO`. The legacy controlled-pilot panel remains available for manual cohorts and a real SMTP GO/NO-GO; it is not a prerequisite for delegated approval to reach `QUEUED` while dispatch is paused. A blocked account does not roll back successful accounts, and retries reuse the exact touchpoint/draft/idempotency binding. No mailbox is relabeled as a named person. Human `APPROVE`, `EDIT`, `REJECT`, `RECIPIENT_CHANGE`, and `SKIP` persist as `HumanCorrection`. Rejection returns copy to a recoverable state; it does not discard the account. DNC, suppression, bounce, target-fit, source freshness, kill switch and dispatch pause remain dominant.

The versioned cohort gate can prepare larger review backlogs without widening any individual authorization. Each cohort remains capped at ten. The next-page action atomically claims a unique supplier CNPJ root and recipient hash, excludes every account with prior outreach history, and returns the cumulative claim count. Recovery re-reads prior cohort suppliers from the current feed, regenerates copy and hashes, and carries no old approval or scheduling. Supplier identity comes from the canonical fornecedor side of the extra-cli feed; contracting authorities are never lead candidates.

Feed freshness uses the upstream manifest's durable `source_generated_at`, not the time at which Warmbly downloaded it. For delegated first touch, the producer-owned `authoritative_source_freshness.expires_at` is a stricter limit and always takes precedence over the generic `CONFENGE_FEED_MAX_AGE` threshold. Warmbly also requires and persists the complete `TARGET_CONFIRMED` membership hash and its TARGET/SUPPLIER counts. The API exposes `feed_authority_state`, `feed_source_expires_at`, `target_membership_complete`, `target_membership_count`, and `supplier_confirmed_count` so an expired or incomplete authority cannot appear `fresh`. The API retains `feed_last_success_at` as a backward-compatible alias for the authoritative source time and exposes `feed_synced_at` separately for operational diagnostics. Missing, expired, stale, corrupt, incomplete, or rolled-back feed state blocks cohort preparation and transport.

The page opens with **INBOUND NOW**: web-cfg leads that already have a durable receipt, recommended next action, owner or explicit UNKNOWN, and commercial-latency timestamps. Then **O que fazer agora**: only executable human work (calls, routed calls, first-touch exceptions, role mailboxes, WhatsApp, professional profiles, forms). Each card shows company, person or target role, route class, why now, offer, channel, reachability class, confidence, factual hook, evidence, warnings, channel-appropriate copy, last outcome, and next action, plus a Revisar / copiar control. Calls, WhatsApp, social, forms and anything outside the first-touch policy remain human-executed only. Inbound classification may recommend `SEND_EMAIL` in review. It never dispatches.

The commercial-intelligence panel is followed by **Fila de exceções**: orphans, conflicts, and impossible transitions. The operator can filter by type, lane, age, source, and severity, open evidence and history, and take only `link`, `defer`, `reject`, or `mark_external_evidence_required`. There is no control that invents WON, LOST, revenue, or identity. UNKNOWN stays UNKNOWN. The same actions exist on `confenge intel-exceptions` when there is no UI.

The operational funnel counts imported tiers, human exceptions in `NEEDS_REVIEW`, delegated approvals/readbacks, manual lanes, planned and actionable work, and post-send outcomes from the cockpit and first-touch status endpoints. Each manual-lane card shows why now, the factual hook, the recommended action, confidence, and a Copy text control. The per-message review queue shows only work that actually needs human judgment; the operator can approve, adjust, reject, skip, hold or mark the account as do not contact.

## Commercial actions

The executive response includes a weekly revenue-chain read model for operational consoles. Every row is keyed by an opaque `correlation_id`, never by a company or contact name. Warmbly owns commercial actions and their outcomes. The console may operate and display those facts, while Asaas remains the financial authority for charge and receipt status.

The chain keeps charge creation separate from confirmed and received payment. A missing proposal, charge, receipt, owner, deadline, or next action is explicitly `UNKNOWN`; missing money does not become `0`. Human commercial decisions remain visible as `GO`, `NO-GO`, or `WAIT` and are never inferred from provider events. Provider retries use the durable receipt marker and the immutable event timeline, so replaying an already-applied receipt cannot increment revenue again. A missing or malformed provider amount is held for reconciliation instead of borrowing the offer price. A pre-existing correlation stored under a legacy fragmented identity is held for operator reconciliation; Warmbly does not automatically merge historical financial facts.

Actionability is not email sendability. A named person plus a company switchboard is a `ROUTED_CALL` (actionable, not sendable). An inferred email is `INFERRED_EMAIL_REVIEW` and never enters `VALIDATED` or dispatch. A role mailbox is `ROLE_EMAIL`, not a personal inbox. Missing reachability is left empty: Warmbly does not invent an R-class from the current `confenge.outreach.v1` feed.

Execution state (`PLANNED`, `READY`, `IN_PROGRESS`, `COMPLETED`, `NEEDS_FOLLOWUP`, `BLOCKED`) is separate from outcome (`GATEKEEPER_REACHED`, `REFERRED_TO_OTHER_PERSON`, `TARGET_REACHED`, `INTERESTED`, `MEETING_SCHEDULED`, `WRONG_PERSON`, `INVALID_ROUTE`, `DNC`, `QUALIFIED_CONVERSATION`, `PROPOSAL`, `NO_RESPONSE`, `WON`/`CLIENT`, `LOST`). A gatekeeper who names Maria in contratos is new Decision-Unit intelligence, not a failed call. That outcome mints a child action linked to the parent. WON/CLIENT is recorded only by a human, never inferred from a meeting or from inbound interest.

`HumanCorrection` is reused for person, role, route, and DNC feedback (`source = HUMAN_INTERACTION`). It never overwrites upstream evidence. `WRONG_PERSON` and `INVALID_ROUTE` block silent replan of the same person or route.

The extra-cli plug contract (additive fields the future producer can fill) is documented in `docs/confenge/commercial-actions.md`.

## Mailbox capacity and dispatch governor

CONFENGE email pacing is mailbox-first. The campaign scheduler selects an existing email account, and the final transport reservation is bound to that exact account and task. The mailbox's configured `campaign_limit`, `min_wait_time`, readiness, and factual provider state are checked inside the same transaction that reserves the slot. The shared governor remains an additional ceiling across email and WhatsApp. It cannot increase a mailbox envelope.

Only accounts with stored SMTP/IMAP or OAuth credentials are inventoried. A mailbox is blocked when it is disabled, has no assigned worker, lacks credentials, has unknown or failing SPF/DKIM/DMARC state, is quarantined by an existing health authority, or has an unresolved factual authentication, provider-block, rate-limit, or connectivity failure. Provider 4xx/5xx responses, hard bounces, complaints, replies, attempts, and acceptances remain separate observations. A bounce or complaint rate does not create a new threshold here. Existing explicit campaign/provider policies remain authoritative.

For each mailbox, the hourly cap is derived from the minimum wait and tightened by any explicit cap. The daily cap is the configured mailbox campaign limit. Attempts that reached the provider consume that daily envelope even when the provider later rejects them. A growing queue cannot raise either cap, and retries retain the same account/recipient/sequence idempotency key across mailboxes.

The status forecast simulates the configured business window, business days, mailbox daily and rolling-hour limits, minimum wait, occupied reservations, observed attempts, provider acceptances, and the shared ceiling. It returns slots for the next 24 hours and 7 days and an estimated queue drain time only while effective capacity exists. During a pause, effective slots are zero and potential slots remain visible. These are possible attempt slots, not promised deliveries.
